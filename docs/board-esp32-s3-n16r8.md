# ESP32-S3-DevKitC-1 N16R8 + GC9A01: правила работы

Записано после отладки на живой плате. Всё здесь проверено на железе, а не
взято из даташита, — каждая ловушка стоила отдельного разбора.

## Распиновка

| Пин дисплея | GPIO | Почему именно этот |
|---|---|---|
| SCL / SCK | **12** | пин IO MUX шины SPI2 — только на таких держится 80 МГц |
| SDA / MOSI | **11** | IO MUX SPI2 |
| CS | **10** | IO MUX SPI2 |
| DC / RS | **13** | свободный |
| RST | **14** | свободный |
| BL / LED | **21** | свободный; если подсветка впаяна на 3V3 — не подключать |
| VCC | 3V3 | не 5 В |
| GND | GND | |

MISO к дисплею не идёт — панель только принимает.

## Что на этой плате занято и трогать нельзя

| GPIO | Кем занято |
|---|---|
| 26–32 | флеш |
| **33–37** | **октальная PSRAM** — это и есть R8 в названии |
| 0, 3, 45, 46 | strapping-пины, состояние при старте меняет режим загрузки |
| 19, 20 | нативный USB |
| 43, 44 | UART0, он же вывод в монитор порта |

Свободны: 1–18, 21, 38–42, 47, 48. На части ревизий DevKitC-1 GPIO38 или
GPIO48 заняты адресным светодиодом — если нужен именно он, проверь по плате.

## Ловушка 1: шина отбирает пин под MISO

**Симптом:** подсветка горит, экран чёрный, прошивка при этом работает и
исправно пишет в монитор порта.

`SPIClass::begin(sck, miso, mosi, ss)` при `miso = -1` **не оставляет линию в
покое**. Он подставляет штатный пин шины и выполняет для него `pinMode(INPUT)`:

| Чип и шина | Какой пин заберёт |
|---|---|
| ESP32-S3, FSPI | **GPIO13** |
| ESP32-S2, FSPI | GPIO37 |
| ESP32, HSPI | GPIO12 |
| ESP32, VSPI | GPIO19 |

У нас DC как раз на GPIO13. `begin()` вызывается после нашего
`pinMode(PIN_DC, OUTPUT)` и перебивает его — DC становится входом, панель
перестаёт различать команды и данные и не просыпается вообще.

**Правило:** всегда передавать в `begin()` **заведомо свободный** пин под MISO
(`PIN_MISO` в `include/config.h`), а `pinMode()` для CS и DC повторять уже
после старта шины. Оба действия есть в `gc9a01::begin()`.

## Ловушка 2: Serial уходит не в тот порт

У платы два разъёма USB: **UART** (мост CH343, `1a86:55d3`) и **нативный USB**
самого S3. Куда попадёт `Serial`, решает флаг сборки:

| Флаг | Куда идёт Serial |
|---|---|
| `-DARDUINO_USB_CDC_ON_BOOT=0` | UART0 → мост CH343 → `/dev/ttyACM0` |
| `-DARDUINO_USB_CDC_ON_BOOT=1` | нативный USB S3 (порт появляется, только когда прошивка запущена) |

Проект собран под мост (`=0`). Понять, каким разъёмом подключено:

```bash
ls /dev/serial/by-id/          # 1a86_USB_Single_Serial -> мост, ставь 0
lsusb | grep -i 303a           # 303a:1001 -> нативный USB, ставь 1
```

Если флаг не тот, загрузка всё равно пройдёт (esptool говорит через мост),
но вывод программы будет уходить в никуда, и плата покажется зависшей.

## Ловушка 3: инициализацию панели нельзя слать на быстрой шине

**Симптом, который ни с чем не спутать:** экран чёрный, прошивка работает и
пишет в порт, а после очередной перезагрузки панель вдруг заводится. Потом
опять не заводится.

Инициализация — это несколько десятков байт один раз за запуск, её скорость
не значит ничего. Зато цена ошибки несимметрична: **не дойдёт один байт
таблицы — контроллер не проснётся вообще**, а сбой при передаче пикселей даст
в худшем случае рябь на одном кадре.

Поэтому таблица уходит на `SPI_HZ_INIT` (10 МГц), и только после неё
вызывается `setClock(SPI_HZ)` для пикселей. Частота, кстати, применяется не в
`begin()` шины, а при открытии транзакции, так что переключать её нужно именно
так, а не присваиванием.

Рабочая частота по умолчанию — 40 МГц (38 кадров в секунду). 80 МГц дают 50
кадров, но на перемычках срываются; поднимать стоит, только когда дисплей
сядет на нормальный шлейф.

## Настройки среды в platformio.ini

```ini
board = esp32-s3-devkitc-1
board_upload.flash_size = 16MB
board_build.flash_mode = qio
board_build.arduino.memory_type = qio_opi   ; флеш QIO + октальная PSRAM
board_build.partitions = default_16MB.csv
```

`qio_opi` обязателен: у N16R8 PSRAM октальная. С настройкой по умолчанию плата
либо не увидит PSRAM, либо будет перезагружаться.

## Память: проверено на плате

Прошивка печатает состояние памяти при каждом старте (`reportMemory()` в
`src/main.cpp`). На N16R8 должно быть так:

```
RAM:   всего 323780, свободно 298800 байт
PSRAM: всего 8386279, свободно 8386035 байт
```

**Ноль в строке PSRAM** означает, что в `platformio.ini` потеряно
`board_build.arduino.memory_type = qio_opi` или флаг `-DBOARD_HAS_PSRAM`.
Плата при этом работает, просто восьми мегабайт как не бывало.

Внутренней RAM показано меньше 512 КБ, потому что часть съедена статическими
буферами прошивки и служебными областями: в куче остаётся то, что свободно.
Наши буферы кадра (маска 240×140, ореол и полоса вывода, всего около 62 КБ)
лежат в статической памяти и в этот счёт не попадают.

**Лицо намеренно не использует PSRAM.** Она идёт через внешнюю шину и в разы
медленнее внутренней; маска покрытия перечитывается на каждый пиксель кадра,
и вынос её в PSRAM убил бы частоту кадров. PSRAM держим под голосовую часть —
буферы записи, модели, очереди аудио. Выделять оттуда:

```cpp
void *buf = ps_malloc(size);                              // или
void *buf = heap_caps_malloc(size, MALLOC_CAP_SPIRAM);
```

## Прошивка

```bash
pio run -e s3n16r8 -t upload --upload-port /dev/ttyACM0
pio device monitor -e s3n16r8
```

Порт не находится — зажать BOOT, коротко нажать RESET, отпустить BOOT.
Если прошивка уже заливается и пишет в монитор, BOOT больше не нужен:
проблема не в загрузке, а в схеме или в коде.

## Как искать неисправность

Порядок, который реально сработал:

1. **Прошивка вообще запускается?** Читаем порт. Если видно `Stack smashing
   protect failure` или перезагрузки по кругу — это наш баг, декодируем:
   ```bash
   xtensa-esp32s3-elf-addr2line -pfiaC -e .pio/build/s3n16r8/firmware.elf 0x4200...
   ```
   Тулчейн лежит в `~/.platformio/packages/toolchain-xtensa-esp32s3/bin/`.
2. **Панель принимает данные?** Отдельная прошивка `paneltest`: мигание
   подсветкой, сплошные заливки, маркеры краёв и шахматка на шине 10 МГц.
   ```bash
   pio run -e paneltest -t upload
   ```
3. **Держит ли пайка частоту?** В `src/main.cpp` есть `clockProbe()` — заливает
   экран своим цветом на 80, 40, 20 и 10 МГц (красный, зелёный, синий, белый).
   Включается флагом `-DCLOCK_PROBE`. Какие цвета видно — такие частоты рабочие.
4. **Куда уходит время кадра?** В монитор каждые три секунды печатается
   профиль стадий.

## Замеры производительности

Лицо 240×240, живая полоса 140 строк, ESP32-S3 на 240 МГц:

| Стадия | мкс на кадр |
|---|---|
| контуры Безье в маску | 1 500 |
| ореол (уменьшение + два box-фильтра) | 3 070 |
| композит в RGB565 | 6 300 |
| выгрузка по SPI на 40 МГц | 15 560 |
| **итого** | **26 000 → 38 FPS** |

На 80 МГц выгрузка занимает 8.9 мс, это 50 FPS, но см. ловушку 3.
На 20 МГц — примерно 25 FPS.

Что дало ускорение с исходных 19.8 FPS:

* **активный список рёбер** вместо перебора всех при заливке по строкам:
  14.9 мс → 1.5 мс. Рёбра разложены по строке, с которой начинаются, на каждой
  подстроке перебираются только несколько активных;
* **целочисленный композит** вместо float, плюс пропуск участков строки, где
  нет ни маски, ни ореола: 15.6 мс → 6.3 мс;
* **box-фильтр без деления** (умножение на обратное) и без `clamp` в горячем
  цикле: 4.4 мс → 3.1 мс;
* **шина 80 МГц** вместо 40: 15.6 мс → 8.9 мс.

## Прочее, на чём обожглись

* Таблица инициализации панели читается парами «команда, длина». Терминатор
  тоже обязан быть парой `0x00, 0x00` — иначе за концом массива подхватывается
  мусор, попадает в счётчик аргументов и уезжает за границу буфера на стеке.
  Ловится как `Stack smashing protect failure` в `gc9a01::begin()`.
* Длину аргументов из таблицы стоит ограничивать размером буфера, даже если
  таблица заведомо правильная.
